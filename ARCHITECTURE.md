## Canonical people and confidentiality

- `people` contains shared name, email and phone, scoped to its recruiter. A name and email or phone are required. Email is lowercased; phone matching/indexing removes formatting. Unique owner/email and owner/normalized-phone indexes prevent exact duplicates within a workspace.
- `company_contacts` links a person to a company with position and business relationship notes. A person/company pair is unique; one person can have several company relationships.
- `candidate_profiles` adds confidential candidate notes, current title/employer, general pay expectations, availability, location and skills. The same person ID can have both a candidate profile and company contacts.
- Its optional `linkedin_url` is a length-checked HTTPS LinkedIn personal-profile link. Candidate forms trim/normalize share URLs and detail view opens the link with noopener/noreferrer. `save_person_record` accepts explicit null to clear it while preserving it when an older caller omits the key. It remains absent from contact-only queries; no external integration or template change is introduced.
- `candidate_files` stores private CV metadata, status and content hashes against the candidate profile.

New forms search existing people and require explicit reuse; name similarity never silently merges records. Candidate profiles already present open canonically. Shared identity edits propagate to both contexts. Contact queries/previews deliberately fetch shared identity and business relationships only; they do not query candidate profiles/files or render their pay/private notes.

Compensation is recorded as text, including currency and period. The pay filter explicitly searches that text; it does not convert currencies or interpret numeric ranges. Candidate general expectations, role budgets and application discussed salary are separate fields.

The operator-only fictional UAT refresh lives under `scripts/uat`, separate from migrations and application code. A local generator creates deterministic IDs, PDF CVs and a one-transaction refresh requiring the exact pre-refresh snapshot. Normal workflow functions create history, conversation follow-ups, submissions, accepted offers and placement ledgers under authenticated owner RLS; triggers/access policies remain enabled. Original known sample journeys are replaced only after the guarded comparison; other accounts/preferences are untouched. An isolated rollback-only variant verifies the full graph. Historical event dates provide the six-month portfolio chronology; immutable placements retain their real insertion timestamps. See UAT_DATA.md for the current loading checkpoint.

## Roles, applications and terms

Roles belong to a company; an optional hiring contact must belong to that same company/account. Company ownership cannot be reparented after creation. Role status (Briefing/Active/On hold/Closed) is separate from Normal/Urgent priority. Nullable company default and role override percentages accept 0–100 with two decimal places; explicit zero is preserved. Blank override follows the current default, blank default is unset. No fee amount, salary basis or placement agreement is inferred.

Applications have one unique role/person pair and immutable identity/links. Both candidate and role views use the same application ID. Response and stage never automatically change each other. Five active stages are Identified, Screening, Submitted, Interview and Offer. Stage Closed or response Declined/Withdrawn is retained in the closed pipeline. New links start Identified/Not contacted; closed roles reject new applications but return existing canonical links on retry.

`link_applications` saves up to 100 selected pairs atomically with initial history. It locks roles consistently and returns existing pairs without duplicate events. `record_application_update` locks the application, checks its integer version and saves state plus one event in a transaction. A stable event UUID and exact request comparison make an uncertain response safe to retry. A stale version or different payload with a reused event ID is rejected. Role edits also compare/increment integer versions; creates use stable draft IDs and payload comparison.

Every application insert/update appends a trigger-generated application_event with server snapshots. Clients cannot directly forge, update or delete history. Events retain the entered Hong Kong date (today or earlier) and separate server recording timestamp, ordered by event date then recording time. Backdated updates still change the current application state; their date locates the historical note, not an automatic state replay. Each event describes one application; activity_outcomes links conversation events to their shared conversation.

## Conversations and daily work

`activities` is one immutable candidate conversation with title/channel/date/general notes and the original request payload. `activity_outcomes` connects each selected application to its new, server-generated history event. Before/after application values live in that existing event, not a competing application state. Candidate history groups the conversation once; applications link back to that canonical conversation. Contact/company People loaders do not read candidate conversations or tasks.

`record_candidate_activity` locks the candidate, checks a stable request UUID and exact payload, and inserts the activity. Before/after insert triggers enforce the full transaction even for a direct Data API insert. They validate candidate ownership, reject duplicate selections and pre-existing history-event IDs, update applications in stable ID order through the existing versioned RPC, link those events, create only selected tasks and optionally apply confirmed general expected pay/notice changes. Profile updates check the original timestamp and retain server before/after values. Stale or invalid outcomes/tasks/profile changes roll back the entire transaction. General notes and role-specific outcome notes remain separate; application opportunity notes are preserved.

`tasks` stores an action, optional due date/time (Hong Kong wall time), Normal/High priority, notes and completion timestamp. A standalone task chooses general/candidate/company/role/application context; application/role context inherits canonical links on the server. Source follow-ups retain their original conversation/application. Composite references, validation triggers and forced owner/approval RLS reject mismatched accounts/candidates/companies. Conversations/outcomes have no client update/delete grants; tasks have no delete grant.

Task creates retain stable UUIDs; retries compare the entered fields and chosen context, allowing server-inherited links/time normalization. Task edits compare/increment integer versions. `set_task_completion` records completion or reopens a task, supports same-version retry without duplicate changes and rejects stale conflicting actions. Completion never records contact/submission or changes application state.

Today/Tasks use date-based Overdue, Due today, Upcoming, Unscheduled and Completed groups. Date-only tasks become overdue on the following Hong Kong day; an optional clock time orders same-day tasks without making them overdue during that day. Today displays the first six due tasks, five upcoming tasks within seven days, and real loaded-record counts. A minute/focus/visibility day check keeps the date grouping current across midnight; it does not poll database changes. Lists/history/options remain subject to the existing API row limit (POC-011). No reminders, notifications, recurring tasks, team assignment or communication sending were added.

## Submissions through placement

`submissions` groups selected applications for one role with a recipient snapshot, actual sent date and notes. `submission_items` links each selection to its fresh application history event. The user confirms the shortlist was already sent. Only selected applications are updated: Identified/Screening becomes Submitted; later stages remain. Same-company contact validation, sorted application locks, exact retries and insert triggers prevent partial/duplicate groups, including direct Data API inserts.

`application_steps` stores immutable Feedback, Interview or Offer details against the same canonical application event ID and resulting application version. Server validation normalizes the kind's finite fields. Client decisions can advance/close the stage; interview arrangements retain future Hong Kong logistics separately from their recording date. Outreach response, discussed pay, general expectations and other applications stay unchanged. New offer records retain earlier decisions. Only the latest accepted offer on an active Offer-stage application can become a placement.

`placements` has one unique application and immutable links, accepted-offer salary, names/start date and agreed commercial snapshot. It records explicit currency, fee mode/source, fee-basis amount/description, percentage or fixed fee, guarantee dates/terms and notes. Inherited percentages are rechecked at save. PostgreSQL numeric and client integer calculations use two decimals and positive half-up rounding; no salary multiplier or currency conversion is inferred. Creation atomically closes the application and records its history. Placed applications cannot be reopened, and offer steps cannot rewrite a placed agreement.

`placement_events` is an append-only invoice/payment/guarantee ledger. The latest invoice entry is the current revision of one invoice. Issued invoices require reference/issue date; positive payment entries cannot exceed the outstanding same-currency balance. A reasoned payment-void entry corrects recorded totals while retaining the original entry; no refund occurs. Paid balances do not complete guarantees. The latest check-in records who was contacted, method/outcome and explicit guarantee status. Current state follows server versions, even for a backdated entry; dates alone do not auto-complete guarantees.

Commercial RPCs use stable UUIDs/exact payloads and approved-owner RLS. Insert triggers enforce state/history/selected-task writes as one transaction even for direct inserts. Agreement UPDATE is restricted to a version-only bump from a validated event trigger. Placement-event retries use an owner-scoped advisory lock; the insert trigger locks the agreement and rejects stale versions. This avoids FOR UPDATE at RPC depth zero being filtered by the stricter UPDATE policy. All functions are invokers with an empty search path; no privileged frontend/backend credential was introduced.

Selected step tasks retain `source_step_id`. Payment/guarantee follow-ups retain `placement_id`, purpose and inherited application/person/role/company. Sources are immutable; Task detail links to the canonical step/placement. Task completion changes neither financial nor guarantee state. Contact/company People queries do not read these candidate/commercial records.

Agreement amendment, credit notes/refunds/overpayments, taxes, multiple invoices per placement and actual invoice/message/payment sending are outside this batch. Currencies are kept separate in summary metrics. Lists, nested histories and metrics remain subject to API row limits.

## Import, search and personal defaults

`imports.ts` models rows and eligible selection; `import-columns.json` defines the shared template headers. Three static blank workbooks in `public/templates` contain Data/Instructions sheets, text-formatted identity columns and appropriate company validation lists. The templates were authored/rendered with the bundled spreadsheet tools; Artifact Tool is not an application dependency.

`xlsx-import.ts` is dynamically imported when checking a file. Pinned `fflate` 0.8.3 supplies ZIP extraction; native DOMParser reads prefixed/default XML namespaces, inline/shared text and sparse cell addresses. Limits are 1 MB compressed, 8 MB declared expansion, 200 archive entries and 100 nonblank data rows. Paths, formulas, macros/embedded objects/external links, bad headers and numeric phone cells are rejected. The original workbook stays in browser memory and is never stored in Supabase Storage.

`preview_crm_import` is a read-only invoker RPC. It validates template fields, resolves case/outer-space-insensitive company names and normalized email/phone identities, and returns row errors/duplicates/create/reuse actions. Conflicting identity fields or ambiguous/missing company names require manual correction. Reuse rows start unchecked. Existing saved fields are never updated; contacts and new candidate profiles may explicitly reuse a Person. Repeated identities within a file are skipped after the first eligible row.

Confirmation uses a stable batch ID and the exact selected rows/reviewed plan. The import_batches BEFORE INSERT trigger checks approval/ownership, serializes the owner's imports, holds reviewed company/person matches stable, reruns preview and rejects changed/invalid plans before writing. All selected business rows and regenerated results commit together. Direct inserts run the same validation and cannot forge owner/results. Import history has no client update/delete grant; exact RPC retries return the original batch. Confirmed input/results are private; unselected rows are not saved. The client freezes an uncertain confirmation's payload until retry or a definite transaction conflict requires fresh review.

`supporting-api.ts` loads global search, reports and Settings. Search is an invoker SQL union across companies, candidates, contacts, roles, applications, conversations, tasks, placements and submissions. It returns an exact count and 30 rows/page, stable by type/title/ID. Literal substring matching preserves punctuation; a separate normalized-phone match applies only to candidate/contact identities. Contact search uses shared/business fields and never candidate notes. Import history uses an exact count and 20 rows/page. Canonical links retain search/import context.

Analytics aggregates saved rows in an invoker RPC, without client row-limit truncation. Activity cards count distinct officially shortlisted applications and agreements recorded during the selected Hong Kong date/client range; fees are gross agreed amounts grouped by currency. Active roles and attention counts use current state. The cohort starts at each application's first outreach update/conversation with a contact method, excluding structured client steps/shortlists. Reach counts each application once per recorded stage through the end date, without inferring missing stages or completed interviews. Report controls reset correctly with URL/back navigation.

`workspace_preferences` stores approved-owner market/industry/currency defaults with optimistic versions and exact same-payload retries. The shared workspace loader reads them after approval; new company/candidate forms prefill market/industry and new placement agreements use the currency. Defaults are draft baselines, not unsaved edits. Existing records/agreements and Auth/privacy settings remain unchanged. `@types/node` is a development-only dependency for checking exported template files in tests.

Arbitrary spreadsheet mapping, saved-field updates/merges, role/history/CV imports and import undo are outside this batch. Older directory/history pagination, final-host performance and hosted verification remain separate follow-ups.

## Writes, concurrency and drafts

`save_person_record` is a security-invoker PostgreSQL RPC. It saves an identity together with one candidate profile or company relationship in one transaction. It ignores caller-supplied ownership. Composite owner/entity foreign keys reject cross-workspace references. Stable draft IDs and payload comparisons support safe create retries; failures roll back the whole write.

Edits check the original update timestamps and reject stale writes, preserving the local draft. Company editing uses an update-timestamp predicate. A stale or uncertain update may require reload/reconciliation rather than automatic overwrite.

Shared `RecordForm` guards dirty navigation with Keep editing, Save draft & leave and Discard changes. Native before-unload protects refresh/close when there are unsaved changes. Related record previews retain the underlying form and offer opening the canonical record in another tab. Saving before navigation snapshots the destination before async work; it does not rely on a blocker surviving data revalidation. CV selection retains its separate Keep editing / Upload & leave / Discard protection; CV binaries are never form snapshots.

`DraftProvider` wraps the workspace outlet and `useDraftState` explicitly registers durable editor state. `workspaceLoader` reads the requested snapshot after approval, before child form initialization. A canonical route plus draft ID keys the provider: ordinary directory query changes do not remount input controls. `drafts.ts` allowlists supported form routes, validates snapshot shapes, restores Sets/undefined and freezes original IDs/versions/timestamps. Transient errors, preview state, File objects and credentials are excluded. `draft-queries.ts` rejects incompatible, discarded, missing or wrong-route drafts; completed URLs redirect to the saved result.

`form_drafts` stores private snapshots separately from all business tables. Its draft/discarded/completed status is independent of invoice and recruitment statuses. Owners can resume incomplete drafts, soft-discard and restore; normal final Save uses existing validation and write APIs, then completes the draft. The Drafts directory uses title search, allowlisted server ordering/counts and 20-row pages, without loading every payload. Drafts never enter live lists, pipelines, Today or reports. Editing drafts preserve the saved record until final Save, which retains the original stale-write checks rather than silently adopting newer versions.

`save_form_draft` and `set_form_draft_status` are security-invoker RPCs with empty search paths. The table has forced approved-owner RLS, no anonymous/delete grants, immutable owner/route/kind, a versioned format and a 2 MB object-payload limit. Stable IDs, locks, optimistic versions and exact retries reject conflicting edits/transitions. Final Save preflights the draft version; business save and draft completion are separate requests. If only completion fails, the form remembers the confirmed record, locks its fields and offers Finish save/Open saved record instead of replaying the live write. This is recovery for a partial result, not a combined database transaction.

Import drafts store checked rows, reviewed matches/selection, filename and any uncertain confirmation request, without the original workbook. Saving is disabled until a chosen file is checked and while checking. Resuming requires review/confirmation again and retains match/stale checks and stable batch IDs. Checking alone still creates no records; explicit Save as draft persists only the separate snapshot. Unconfirmed changes are not automatically saved.

## Role cards and recruiting indicators

`RoleWorkbench.tsx` replaces the Roles directory table with keyboard-selectable cards and an inline preview. Company/title, location/optional arrangement, age since added, three active-stage counts, a primary indicator, priority and last-update age form the card. The preview leads with Find candidates and the role brief/budget, exposes all applicable indicators and links to the full pipeline/application/record. It is an aid to manual sourcing; recent candidates are ordered by saved update time, not ranked for fit. No new matching engine, score or integration is introduced.

The URL retains search/status/company/priority/work_arrangement/indicator/sort and selected role. Compact sort buttons reuse existing ordering utilities and support legacy sort URLs. Filter/sort changes reset only the card-list scroll; selection changes preserve it. If the selected role is filtered out, the first visible role supplies the preview. Separate scroll areas keep the brief available beside the list. Async preview responses are cancelled logically on selection change; errors have a local retry. Stable detail controls precede async candidate rows to avoid shifting them as data arrives.

`roleFocusData` rechecks approval and fetches only the selected role's three most recently updated active applications and its hiring-contact name. Closed stages/declined/withdrawn responses are filtered on the server before the three-row limit. Candidate fields are limited to name/current title/stage; confidential profile notes/pay/files are not fetched into this preview. Existing candidate/application pages retain their authorized detail flows. Main role-list and full-detail/picker limits remain POC-011.

`role_workbench_summary()` is a stable security-invoker SQL function with empty search path, approved-owner filtering and caller RLS on every underlying read. It aggregates complete pipelines in PostgreSQL rather than counting an API-limited application/history array. Active counts exclude closed/declined/withdrawn applications. No table, ownership policy or privileged credential was added. `roles.work_arrangement` is nullable and constrained to on_site/hybrid/remote; forms, detail and previews use the same labels/validation and normal versioned writes. Existing/older clients that omit the column preserve its saved value.

| Indicator | Recorded rule |
| --- | --- |
| Sourcing needed | Active role with no linked applications, including inactive ones in that zero check |
| No recent progress | Active role with existing applications and at least seven Hong Kong calendar days since progress |
| Awaiting feedback | Active submitted application has a recorded latest submission and no later structured feedback/interview/offer; later replies clear the wait, resubmissions restart it |
| Interview upcoming | Active interview-stage application has its latest saved interview scheduled tomorrow in Hong Kong; pending/confirmed schedules count, without claiming attendance |
| Offer in progress | Active application currently at offer stage |

Progress uses entered application-event/submission dates and linked-task completion dates, bounded below by the role's creation date. Role-brief edits alone do not reset it. Update age separately uses actual saved role/progress timestamps. The UI says Added rather than inventing an opening/reopening history. Hong Kong dates also govern timestamp ages; the existing clock hook refreshes the summary when the day changes. No automatic stage or task changes occur.

Closed/on-hold/briefing roles retain a status chip and suppress active-recruiting warnings. Normally progressing active roles have no warning. When several indicators apply, cards prioritize tomorrow's interview, feedback, offer, sourcing, then stalled progress; the preview retains all. A selected indicator filter takes priority on matching cards, so the visible chip explains the filtered result. Multi-candidate submission ages identify the oldest waiting submission. Awaiting feedback means no later client step recorded in Pairlo, without asserting an external message was unanswered.

`company_recruiting_activity(company,page)` returns an exact total and deterministic 20-row pages under the same invoker/approval/owner boundary. It combines application-event titles/dates/kinds and candidate/role names with company-linked task creation/completion. Canonical application/task links preserve company/page return context. It omits general conversation bodies, candidate notes, pay, contact methods and CV data. This read-only feed does not create a separate activity log or expose candidate profiles through company-contact queries.

## CV storage and retries

The private `candidate-cvs` bucket allows PDF, Word DOC/DOCX, up to 5 MB. Client checks extension, MIME, basic file signature and size. These checks are not antivirus scanning.

Uploads first create pending metadata. Storage paths are immutable `owner/person/file-UUID`; Storage policies require matching visible metadata for reads and pending metadata for inserts. There are no client rename/overwrite/delete policies. A subsequent identical upload reuses its candidate/content-hash row. Lost/duplicate upload responses are verified against stored bytes before marking ready. Failed uploads remain visibly pending and can be retried by selecting the same file. Binary objects always have a tracked metadata path.

Downloads use authenticated Storage requests, recheck workspace approval and verify byte count/SHA-256 before handing a Blob to the browser. No public or long-lived signed CV URL is generated. Future replacement means a separate version; removal/retention workflows are not implemented.
